# 국가 R&D 과제–기업 매칭: LightGCN · LightFM · HGT 와 bge-m3 임베딩 + LLM 매칭 비교 실험 보고서

- 작성일: 2026-11-16
- 저장소: `apollo.M1.GNN` (브랜치 `feat/local-setup-hits-llm-match`)
- 상태: 실험 진행 중. 이 문서는 실험 설계와 수행 과정까지를 다루며, 결과와 결론은 실험 종료 후 추가한다.

## 1. 서론

### 1.1 배경

국가 R&D 과제의 성과가 기업으로 이전되거나 사업화되려면, 과제와 그 기술을 필요로 하는 기업을 서로 찾아 주는 매칭이 필요하다. 지금까지 APOLLO 매칭 파이프라인(`~/work/apollo`)은 과제·기업 문서의 텍스트 임베딩으로 후보를 검색한 뒤 LLM 이 적합도를 채점해 순위를 정하는 방식을 써 왔다. 이 방식은 문서의 내용 유사성만 보며, 과거에 실제로 일어난 기술이전·사업화·과제수행 관계는 활용하지 않는다.

본 실험은 이 실제 관계를 그래프로 학습하는 모델(LightGCN, HGT)과 행렬 분해 기반 모델(LightFM)이, 텍스트 임베딩 + LLM 매칭 방식에 비해 실제 연결을 얼마나 잘 맞히는지를 같은 조건에서 비교한다.

### 1.2 목적

1. 과제–기업 이분 그래프에서 LightGCN, LightFM, HGT 를 학습하고, 학습에서 제외한 실제 연결(held-out 간선)을 상위 추천에서 얼마나 찾아내는지 측정한다.
2. bge-m3 임베딩으로 후보 100개를 검색하고 LLM 이 재랭킹하는 방식(bge-m3 + LLM)을 같은 쿼리에서 평가해 비교한다.
3. 평가 지표는 Hits@10, Hits@100, NDCG@10, NDCG@100, Recall@10, Recall@100 이다.

### 1.3 비교 대상

| 방법 | 사용하는 정보 | 학습 여부 |
|---|---|---|
| bge-m3 (임베딩 유사도) | 설명문 텍스트 임베딩 | 학습 없음 |
| bge-m3 + LLM | 설명문 텍스트 임베딩 + LLM 적합도 채점 | 학습 없음 |
| LightFM | 임베딩(콘텐츠 피처) + 과제–기업 관계 | 학습 |
| LightGCN | 임베딩(초기 피처) + 그래프 전파 | 학습 |
| HGT | 임베딩(초기 피처) + 관계 타입별 어텐션 전파 | 학습 |

### 2.2 bge-m3 임베딩

초기 실험은 pro-sroberta 키워드 임베딩(768차원, `norm_embed`)을 썼으나, 본 실험부터 **bge-m3 설명문 임베딩(1024차원)** 으로 바꿨다.

- 임베딩 대상 텍스트는 과제설명문·기업설명문이다. 기존 설명문 파일에 있는 행은 그 설명문을 재사용하고, 없는 행은 LLM 으로 설명문을 새로 생성했다.
- 모델은 `BAAI/bge-m3`, 최대 512 토큰, L2 정규화 벡터다. 두 벡터의 내적이 코사인 유사도가 된다.
- 설명문 출처별 건수는 다음과 같다.

| 구분 | 기존 설명문 | 신규 생성 | 설명문 없음 (벡터 없음) |
|---|---|---|---|
| 과제 | 796,014 | 6,696 | 0 |
| 기업 | 364,978 | 27,054 | 425,085 |

### 2.3 벡터가 없는 노드 제외

bge-m3 벡터가 없는 과제·기업은 그래프에서 제외한다 (`config/paths.yaml` 의 `embedding.drop_missing: true`). 제외된 노드는 학습 그래프, 후보 풀, 테스트 어디에도 나타나지 않는다.

- 과제는 모두 벡터가 있어 제외가 없다.
- 기업은 817,117 건 중 425,085 건이 제외되어 **392,032 건**이 남는다.
- 간선이 하나라도 있는 기업 21,204 곳은 모두 벡터가 있다. 따라서 이 제외로 사라지는 간선은 없고, 후보 풀만 줄어든다.

### 2.4 다년도 과제 병합

같은 과제가 연차별로 다른 과제고유번호를 갖는 경우가 많다. `scripts/merge_multiyear_projects.py` 가 다음 규칙으로 병합한다.

1. **안전 병합**: 과제명과 수행기관 집합이 모두 같은 과제를 하나로 합친다.
2. **구체적 과제명 병합**: 수행기관 정보가 없더라도, 과제명이 16자 이상이고 일반 사업명(예: 인력양성, 기반구축) 패턴이 아니면 같은 과제명끼리 합친다.

병합된 과제의 임베딩은 구성 과제 임베딩의 평균을 다시 L2 정규화한 것이고, 대표 ID 는 사전순으로 가장 앞선 과제고유번호다. 간선의 과제 ID 도 대표 ID 로 바꾼다.

- 과제 802,710 건 → **430,374 건** (46.4% 감소; 안전 병합 25,113, 과제명 병합 347,223)

## 3. 지식그래프 생성

### 3.1 그래프 스키마

과제와 기업 두 종류의 노드만 갖는 **이분 이종 그래프**다 (PyTorch Geometric `HeteroData`). 과제–과제, 기업–기업 간선은 만들지 않는다.

| 항목 | 값 |
|---|---|
| 과제 노드 | 430,374 (피처 1024차원) |
| 기업 노드 | 392,032 (피처 1024차원) |
| 간선 타입 | 기술이전(royalty), 사업화(commercial), 과제수행(performance) + 각 역방향 |
| 간선 가중치 | 기술이전 1.0 > 사업화 0.75 > 과제수행 0.5 (`config/graph.yaml`) |

같은 (과제, 기업) 쌍이 여러 관계에 나타나면 관계별 간선으로 각각 유지한다. 임베딩 유사도 간선은 이번 실험의 학습에 쓰지 않았다.

### 3.2 구성 절차 (`src/graph/builder.py`)

1. 노드 테이블을 읽고 벡터 없는 노드를 제외한 뒤 ID ↔ 인덱스 매핑을 고정한다.
2. `bge_m3_embed` 를 float32 행렬로 쌓아 노드 피처로 쓴다.
3. 간선 파일에서 (과제, 기업) 쌍을 뽑아 중복을 제거하고, 노드 매핑에 없는 쌍은 버린다.
4. 관계별로 간선의 10% 를 시드 42 로 무작위 추출해 held-out(테스트) 간선으로 분리한다.
5. held-out 쌍을 **모든 관계**의 학습 간선에서 제거한다 (3.3절).
6. 학습 그래프(`graph.pt`), held-out 간선(`held_out.pt`), 노드 매핑(`node_maps.pkl`)을 저장한다.

### 3.3 held-out 누설 방지

실험 중 다음 문제를 발견해 수정했다. 같은 (과제, 기업) 쌍이 여러 관계에 동시에 나타나는 경우가 많은데, 기존 분할은 관계별로만 간선을 빼서, 한 관계에서 held-out 된 쌍이 다른 관계의 학습 간선으로 남아 있었다.

| 관계 | held-out 간선 | 다른 관계의 학습 간선으로 남아 있던 수 | 비율 |
|---|---|---|---|
| 기술이전 | 1,011 | 497 | 49.2% |
| 사업화 | 3,907 | 1,715 | 43.9% |
| 과제수행 | 4,198 | 1,615 | 38.5% |

이 상태에서는 그래프 모델이 정답 쌍을 학습 그래프에서 그대로 보고 맞힐 수 있다. 그래서 held-out 쌍을 모든 관계의 학습 간선에서 제거하도록 고쳤다 (`config/graph.yaml` 의 `held_out.exclude_pairs_from_all_relations: true`).

### 3.4 최종 간선 수

| 관계 | 학습 간선 | held-out 간선 | 누설 방지로 제거된 학습 간선 |
|---|---|---|---|
| 기술이전 | 8,419 | 1,011 | 678 |
| 사업화 | 33,279 | 3,907 | 1,886 |
| 과제수행 | 35,968 | 4,198 | 1,813 |

### 3.5 설명문의 기업명과 임베딩

과제설명문에는 수행기관명이 적혀 있는 경우가 많고("이 과제는 (주)A 에서 수행했으며 …"), 기업설명문은 업체명으로 시작한다. bge-m3 벡터는 이 원문으로 만들어졌으므로, 임베딩 유사도만으로도 과제와 그 수행 기업이 이름을 통해 가깝게 나온다.

표본 쿼리 599개 중 364개(61%)는 과제 문서에 연결 기업의 이름이 들어 있다. 학습 없이 bge-m3 유사도만으로 검색한 결과를 두 집단으로 나누면 차이가 크다 (전체 관계 합산, 실측).

| 쿼리 집단 | 쿼리 수 | bge-m3 Hits@10 | bge-m3 Hits@100 |
|---|---|---|---|
| 과제 문서에 연결 기업명 있음 | 364 | 0.849 | 0.918 |
| 과제 문서에 연결 기업명 없음 | 235 | 0.226 | 0.332 |

즉 bge-m3 단독 성능의 상당 부분은 기술 내용의 유사성이 아니라 기업명 일치에서 나온다. 같은 벡터를 피처로 쓰는 LightGCN, LightFM, HGT 도 영향을 받는다. LLM 채점 프롬프트에서는 연결 기업명을 가리지만(5.5절), 후보 검색 단계의 임베딩에는 가리기가 적용되지 않는다.

이 때문에 평가 결과는 전체 쿼리와 함께 **두 집단으로 나눈 값**도 보고한다 (`make llm-eval` 의 `name-in-desc`, `no-name`). 기술 내용만으로 매칭하는 능력은 기업명이 없는 집단의 수치가 더 잘 보여 준다. 근본적인 해결은 기업명을 제거한 설명문으로 bge-m3 벡터를 다시 만드는 것이며, 3.6절과 같이 진행하고 있다.

### 3.6 기업명을 제거한 설명문으로 재임베딩

설명문에서 기관명을 제거한 뒤 bge-m3 벡터를 다시 만든다 (`src/data/names.py`, `scripts/build_noname_embed_input.py`). 원래 벡터와 파일은 그대로 두고, 결과는 `~/data/apollo.data/bge_m3_noname/` 에 따로 만든다.

**과제 설명문.**

1. 첫 문장의 "○○에서 수행…" 구문에서 수행기관명을 추출한다 ("이 과제는 ○○에서 수행했으며", "○○에서 수행하는 이 과제는" 두 형태 모두).
2. 그 과제와 기술이전·사업화·과제수행 간선으로 연결된 기업의 업체명을 더한다.
3. 본문 전체에서 이 이름들을 `수행기관` 으로 바꾼다. 법인 형태 표기((주), 주식회사, (재) 등)와 이름 안의 공백 차이는 무시하고 찾는다.

**기업 설명문.** 자기 업체명을 `이 회사` 로 바꾼다.

두 경우 모두 바꾼 말 뒤의 조사(은/는, 을/를, 과/와)를 맞춘다.

| 항목 | 값 |
|---|---|
| 비어 있지 않은 설명문 | 1,194,742 건 |
| 이름 제거로 바뀐 설명문 | 1,107,104 건 (92.7%) |
| `수행기관` 으로 치환된 과제 설명문 | 90.1% |
| `이 회사` 로 치환된 기업 설명문 | 99.9% |
| 연결 기업명이 남아 있는 과제 설명문 | 0 건 |

제거하지 못하는 것은 다음과 같다. 첫 문장에 "○○에서 수행" 구문이 없는 과제 설명문(약 10%)의 수행기관명, 영문명·약칭·브랜드명, 과제명과 키워드에 들어 있는 기업 고유 표현이다.

재임베딩은 완료했다 (과제 802,710 건, 기업 392,032 건). 이후 2.4절의 과제 병합부터 그래프 생성, 모델 학습, LLM 채점까지 전체를 다시 수행한다.

### 3.7 재임베딩 전후의 bge-m3 단독 검색 성능 (실측)

재임베딩이 끝난 뒤, 학습 없이 bge-m3 유사도만으로 검색한 결과를 같은 표본 599쿼리에서 비교했다. 재임베딩 전후의 held-out 간선과 노드 순서는 완전히 같다.

| 구분 | 쿼리 수 | Hits@10 (포함 → 제거) | Hits@100 (포함 → 제거) | NDCG@10 (포함 → 제거) |
|---|---|---|---|---|
| 전체 | 599 | 0.604 → 0.117 | 0.688 → 0.264 | 0.509 → 0.076 |
| 기술이전 | 207 | 0.502 → 0.097 | 0.575 → 0.217 | 0.422 → 0.074 |
| 사업화 | 227 | 0.515 → 0.154 | 0.626 → 0.344 | 0.430 → 0.098 |
| 과제수행 | 220 | 0.786 → 0.100 | 0.855 → 0.245 | 0.686 → 0.056 |
| 과제 문서에 연결 기업명이 있던 쿼리 | 364 | 0.849 → 0.126 | 0.918 → 0.266 | 0.741 → 0.084 |
| 과제 문서에 연결 기업명이 없던 쿼리 | 235 | 0.226 → 0.102 | 0.332 → 0.260 | 0.150 → 0.063 |

- 두 쿼리 집단의 격차가 거의 사라졌다 (Hits@10 0.849 대 0.226 → 0.126 대 0.102). 이름 제거가 의도대로 작동했다.
- 과제수행 관계의 하락이 가장 크다. 설명문에 이름이 적혀 있던 기관이 수행 기업이기 때문이다.
- 과제 문서에 연결 기업명이 없던 쿼리도 Hits@10 이 0.226 에서 0.102 로 내려갔다. 이 쿼리들은 과제 쪽 텍스트가 거의 그대로이고 기업 설명문에서 업체명만 빠진 경우다. 업체명이 업종·기술 단서를 담고 있었을 가능성이 있으나 원인은 확인하지 않았다.

이후의 모든 실험은 기업명을 제거한 벡터를 쓴다. 기업명이 들어간 벡터와 그 결과물은 `~/data/apollo.data/processed/bge_m3_named/` 에 보관했다.

### 3.8 그래프 확장: 특허 · 키워드 · 상속 간선

실제 관계 간선이 있는 노드는 과제의 12.5%, 기업의 5.1% 뿐이다. 더 많은 노드가 간선을 갖도록 세 종류의 간선을 추가했다. 모두 과제–기업 간선이므로 이분 그래프 규칙을 지킨다.

| 간선 | 의미 | 가중치 | 쓰임 | 개수 |
|---|---|---|---|---|
| 특허 (patent) | 과제의 성과 특허를 출원한 기업 | 0.5 (과제수행과 동일) | 학습 양성 + 메시지 전파 | 54,949 |
| 키워드 (keyword) | 과제 키워드와 기업 키워드의 자카드 유사도 상위 | 0.2 | 메시지 전파 전용 | 2,164,060 |
| 상속 (inherited) | 비슷한 과제의 연결 기업, 비슷한 기업의 연결 과제 | 0.2 | 메시지 전파 전용 | 3,965,676 |
| 유사도 상위 10 (기존) | bge-m3 유사도 상위 10 | 0.25 | 메시지 전파 전용 | 7,858,645 |

**특허 간선** (`src/data/patents.py`, `scripts/build_patent_edges.py`). 특허 테이블(`nice_patent_260813.pkl`, 403,024 건)의 각 특허에는 과제번호 목록과 출원기관 사업자번호가 있다. 과제번호를 다년도 병합의 대표 ID 로 바꾼 뒤 (과제, 출원 기업) 쌍을 만든다.

| 항목 | 값 |
|---|---|
| 특허에서 뽑은 (과제, 출원 기업) 쌍 | 165,157 |
| 양쪽이 모두 그래프에 있는 쌍 | 57,416 |
| held-out 쌍과 같아 제거한 쌍 | 2,467 |
| 학습 간선으로 추가한 쌍 | 54,949 |

출원기관의 다수는 연구소·대학이라 기업 노드와 매칭되는 비율은 34.8% 다. 특허 간선은 학습에만 쓰고 held-out 으로 분리하지 않으므로, 평가 대상은 기존 3종 관계 그대로이고 held-out 집합도 이전과 같다. 학습 양성 간선은 77,666 개에서 132,615 개로 늘었다.

**키워드 간선** (`src/graph/aux_edges.py::keyword_edges`). 과제 키워드 집합과 기업 키워드 집합의 자카드 유사도로, 과제마다 상위 5개 기업과 기업마다 상위 5개 과제를 잇는다(합집합).

- 공통 키워드가 2개 이상인 쌍만 대상으로 한다.
- 2,000 개 넘는 과제 또는 기업에 나오는 흔한 키워드(예: 소프트웨어, 반도체)는 제외한다. 제외하지 않으면 공통 키워드를 가진 쌍이 약 22억 개가 된다.
- 간선이 생긴 노드는 과제의 81.3%, 기업의 53.5% 다. 자카드 값은 낮다(중앙값 0.048). 과제 키워드는 평균 40개의 긴 기술 구문이고 기업 키워드는 평균 16개의 짧은 업종 용어라 겹침이 적기 때문이다.

**상속 간선** (`src/graph/aux_edges.py::inherited_edges`). 같은 타입의 비슷한 노드가 가진 연결 상대를 물려받는다. 유사도는 bge-m3 벡터의 내적(코사인)이다.

- 과제 쪽: 과제 p 와 가장 비슷한 과제 5개(학습 간선이 있는 과제 중, 자기 자신 제외)의 연결 기업을 p 에 잇는다.
- 기업 쪽: 기업 c 와 가장 비슷한 기업 5곳의 연결 과제를 c 에 잇는다.
- 후보마다 그것을 가진 이웃들의 유사도 합을 점수로 하고, 노드마다 상위 5개를 남긴다.
- 학습 간선만 보고 상속하므로 held-out 정보는 쓰이지 않는다.
- 간선이 생긴 노드는 과제의 99.9%, 기업의 100% 다. 이웃 유사도 합의 중앙값은 0.83 이다.

**메시지 전파 전용으로 쓰는 이유.** 키워드·상속 간선은 추정 간선이고 수가 수백만 개다. 학습 양성으로 넣으면 실제 연결 13만 개를 압도한다. 그래서 유사도 간선과 같이 메시지 전파에만 쓴다. 약한 가중치는 LightGCN 에서 메시지에 곱해 반영한다. HGT 는 구조상 간선 가중치를 받지 못하며 관계별 어텐션이 그 역할을 한다.

**held-out 쌍 점검.** 추가한 간선과 기존 간선에 held-out 정답 쌍이 들어 있는지 확인하고 모두 제거했다.

| 간선 | held-out 정답과 같은 쌍 | 조치 |
|---|---|---|
| 특허 | 2,467 (held-out 쌍의 28%) | 그래프 생성 때 학습 간선에서 제거 |
| 유사도 상위 10 (기존) | 1,392 (15.7%) | 학습 때 메시지 전파에서 제거 |
| 키워드, 상속 | 0 | 생성 단계에서 학습 쌍과 held-out 쌍을 모두 제외 |

유사도 간선의 1,392 쌍은 정답 라벨을 써서 생긴 것이 아니라 bge-m3 가 맞힌 쌍이다. 다만 평가 대상 쌍이 직접 이웃으로 주어지면 그 쌍의 평가가 임베딩 검색의 결과와 섞이므로, 학습 쌍과 같은 취급으로 제외했다 (`config/graph.yaml` 의 `auxiliary_edges.drop_held_out_pairs`). 이 변경 전의 GNN 결과(7.2절)에는 이 1,392 쌍의 영향이 포함되어 있다.

**같은 타입 유사성의 대안.** 현재는 bge-m3 코사인만 쓴다. 보완책은 다음과 같으며, 현재 방식의 결과를 본 뒤 적용 여부를 정한다.

| 방법 | 기대 효과 |
|---|---|
| bge-m3 코사인과 키워드 자카드의 결합 | 문장 유사도와 용어 일치를 함께 반영 |
| 상호 최근접 이웃만 인정 | 한쪽만 가깝다고 본 오연결 감소 |
| 유사도 하한 적용 | 충분히 비슷하지 않은 이웃 제외 (현재 하한 0) |
| 기업: 산업분류 일치 조건 | 업종이 다른 기업 간의 우연한 유사 제거 |
| 과제: 특허 IPC 코드 공유 | 임베딩과 독립된 기술 분류 정보 활용 |

## 4. 모델 소개

### 4.1 LightGCN

LightGCN (He et al., SIGIR 2020) 은 추천을 위해 GCN 을 단순화한 모델이다. 층마다 있던 피처 변환 행렬과 비선형 활성 함수를 없애고, 이웃 임베딩을 정규화해 더하는 전파만 남겼다.

- 전파: 각 노드의 다음 층 임베딩은 이웃 임베딩의 합이며, 간선마다 1/√(deg(u)·deg(v)) 로 정규화한다.
- 층 결합: 0층부터 L층까지의 임베딩을 평균해 최종 임베딩으로 쓴다.
- 특징: 파라미터가 적고 학습이 빠르다. 협업 필터링 신호(누가 누구와 연결됐는가)를 직접 전파한다.

### 4.2 LightFM

LightFM (Kula, 2015) 은 협업 필터링과 콘텐츠 기반 추천을 결합한 하이브리드 행렬 분해 모델이다. 사용자·아이템의 잠재 벡터를 각자의 피처 임베딩의 합으로 표현한다.

- 점수: 과제 잠재 벡터와 기업 잠재 벡터의 내적 + 편향.
- 손실: WARP (Weighted Approximate-Rank Pairwise). 양성 쌍보다 높은 점수를 받는 음성 쌍을 찾을 때까지 샘플링해, 상위 순위 정확도를 직접 최적화한다.
- 특징: 그래프 전파가 없다. 피처만으로 잠재 벡터를 만들 수 있어 간선이 없는 노드(cold start)도 다룰 수 있다.

### 4.3 HGT

HGT (Heterogeneous Graph Transformer; Hu et al., WWW 2020) 는 노드 타입과 간선 타입이 여럿인 그래프를 위한 어텐션 기반 GNN 이다.

- 노드 타입별·간선 타입별로 다른 파라미터의 어텐션을 쓴다. 메시지를 보내는 노드 타입, 간선 타입, 받는 노드 타입의 조합마다 가중치가 다르다.
- 다중 헤드 어텐션으로 이웃의 중요도를 학습해 가중 합산한다.
- 특징: 기술이전·사업화·과제수행을 서로 다른 관계로 구분해 학습할 수 있다. 계산량과 파라미터가 LightGCN 보다 많다.

## 5. 구현 방법

### 5.1 공통 학습 절차 (LightGCN, HGT)

두 GNN 은 인코더만 다르고 학습 루프는 같다 (`scripts/train_gnn.py`, `src/training/trainer.py`, `src/training/sampler.py`, `src/training/losses.py`).

아래 표와 설명은 **처음 사용한 기본 설정**이다. 이 설정에서 학습이 붕괴하는 문제가 확인되어 음성 샘플링과 메시지 전파 방식을 바꿨다. 변경 경과와 현재 설정은 5.6절에 정리했다.

| 항목 | 값 |
|---|---|
| 초기 노드 피처 | bge-m3 임베딩 1024차원 → 노드 타입별 선형층 → 128차원 |
| 은닉·출력 차원 | 128 |
| 층 수 | 2 |
| 손실 | 간선 타입 가중 BPR (기술이전 1.0, 사업화 0.75, 과제수행 0.5) |
| 음성 샘플 | 양성 간선당 무작위 기업 5개 |
| 학습 방향 | 과제 → 기업 |
| 에폭 / 배치 | 30 / 4,096 |
| 최적화 | 학습률 1e-3, weight decay 1e-5 |
| 출력 | L2 정규화된 z (내적 = 코사인) |
| 시드 | 42 |

**미니배치 구성** (`EdgeSampler`). 세 관계의 학습 간선(총 77,666개)을 하나로 모아 에폭마다 무작위로 섞고 4,096개씩 나눈다. 각 양성 간선 (과제 p, 기업 c) 에 대해 전체 기업 392,032 곳에서 음성 기업 5개를 균등 무작위로 뽑는다. 각 간선에는 그 관계의 가중치 w 가 붙는다. 한 에폭은 19 스텝이다.

**순전파.** 스텝마다 전체 그래프를 인코더에 한 번 통과시켜 모든 노드의 z 를 얻는다 (이웃 샘플링 없이 전체 그래프 전파). 그 뒤 배치에 해당하는 과제·기업의 z 만 골라 점수를 계산한다.

- 양성 점수: s⁺ = z_p · z_c
- 음성 점수: s⁻_k = z_p · z_{c'_k} (k = 1…5)

**손실** (`bpr_loss`). 간선 타입 가중 BPR 이다.

```
L = 평균_{배치, k} [ − w · log σ( s⁺ − s⁻_k ) ]
```

σ 는 시그모이드, w 는 간선 타입 가중치다. 기술이전 간선의 순위 오류가 과제수행 간선보다 두 배 크게 반영된다.

**최적화와 출력.** Adam 으로 30 에폭 학습한다. 학습 후 평가 모드로 전체 그래프를 한 번 더 통과시켜 과제·기업의 z 를 `data/processed/project_z_<태그>.npy`, `company_z_<태그>.npy` 로 저장한다.

**추론.** 쿼리 과제의 z 와 전체 기업 z 의 내적을 계산해 상위 100개를 반환한다. z 가 L2 정규화되어 있어 내적이 코사인 유사도다. 이미 연결된 기업도 결과에서 제외하지 않는다.

### 5.2 LightGCN 구현 (`src/models/lightgcn.py`)

PyG 의 `LGConv` 는 이분 그래프의 (출발, 도착) 피처 쌍을 받지 못해, 전파를 직접 구현했다.

**0층 임베딩.** 원 논문은 노드마다 학습 가능한 ID 임베딩을 쓴다. 본 구현은 그 대신 bge-m3 임베딩을 노드 타입별 선형층으로 변환한 값을 쓴다.

```
h⁰_v = W_τ(v) · x_v + b_τ(v)        (τ(v): 노드 v 의 타입, x_v: bge-m3 벡터)
```

이렇게 하면 간선이 없는 노드도 임베딩을 가지며, 학습 파라미터가 노드 수에 비례하지 않는다.

**전파.** 관계 r (역방향 포함 6개) 마다 대칭 정규화 전파를 계산하고, 모든 관계의 메시지를 더한다. 변환 행렬과 활성 함수는 없다.

```
h^{l+1}_v = Σ_r Σ_{u ∈ N_r(v)}  h^l_u / √( deg_r(u) · deg_r(v) )
```

deg_r 은 관계 r 안에서의 차수다. `scatter_add` 로 구현했다. 간선 타입 가중치를 메시지에 곱하는 옵션(`--mp-edge-weights`)이 있으나 이번 실험에서는 쓰지 않았다.

**층 결합과 출력.** 0, 1, 2층 임베딩의 평균을 L2 정규화해 z 로 쓴다.

```
z_v = normalize( (h⁰_v + h¹_v + h²_v) / 3 )
```

**파라미터.** 학습되는 것은 입력 선형층 두 개(과제용, 기업용)뿐이며 총 262,400 개다. 에폭당 약 4초가 걸린다.

**간선이 없는 노드.** 전파로 받는 메시지가 없어 1, 2층 임베딩이 0 이 되고, z 는 h⁰ 의 방향으로만 결정된다. 기업의 약 95% 가 여기에 해당한다.

### 5.3 HGT 구현 (`src/models/encoder.py`)

PyG 의 `HGTConv` 를 사용했다.

**구조.**

```
x_v → 타입별 선형층(1024→128) → [HGTConv → ReLU → Dropout(0.1)] × 2 → 타입별 선형층(128→128) → L2 정규화 → z_v
```

**HGTConv 한 층의 계산.** 도착 노드 t, 출발 노드 s, 간선 타입 r 에 대해 다음을 계산한다 (헤드 4개, 헤드당 32차원).

1. 타입별 사영: 출발 노드는 Key 와 Value 로, 도착 노드는 Query 로 사영한다. 사영 행렬은 노드 타입마다 다르다.
2. 관계별 어텐션: 어텐션 점수는 Key 를 간선 타입 r 의 행렬로 변환한 뒤 Query 와 내적하고, 관계별 사전 가중치를 곱해 구한다. 한 도착 노드의 모든 이웃에 대해 softmax 로 정규화한다.
3. 관계별 메시지: Value 를 간선 타입 r 의 행렬로 변환한다.
4. 집계: 메시지를 어텐션 가중치로 가중 합산하고, 도착 노드 타입별 선형층을 거친 뒤 이전 층 표현과 학습 가능한 비율로 섞는다 (skip 연결).

```
α(s, r, t) = softmax_{s ∈ N(t)} [ ( K(s) · W^ATT_r · Q(t)ᵀ ) · μ_r / √d ]
h_t ← A_τ(t)( Σ_{s ∈ N(t)} α(s, r, t) · V(s) · W^MSG_r ) 와 이전 h_t 의 가중 결합
```

기술이전·사업화·과제수행과 각 역방향 6개 간선 타입이 서로 다른 W^ATT_r, W^MSG_r 를 갖는다. 그래서 "기술이전으로 연결된 이웃"과 "과제수행으로 연결된 이웃"을 다르게 반영할 수 있다.

**파라미터.** 실제 관계 3종 그래프에서 총 657,972 개다. 에폭당 약 85~90초가 걸린다 (LightGCN 의 약 20배). 확장 그래프에서는 간선 타입이 늘어 789,108 개다.

**미니배치 학습** (`src/training/neighbor_sampler.py`, `config/train.yaml` 의 `gnn.minibatch`). 전체 그래프 학습은 스텝마다 모든 노드를 인코딩하므로 메모리 사용량이 간선 수에 비례한다. 미니배치 학습은 스텝마다 그 배치의 양성·음성 노드만 인코딩한다.

1. 배치의 과제와 기업(양성, 음성 모두)을 시드 노드로 둔다.
2. 시드 노드마다 관계별로 유입 간선을 최대 10개 뽑는다 (1홉). 여기서 새로 나온 노드와 시드 노드에 대해 다시 관계별로 최대 5개를 뽑는다 (2홉).
3. 첫 번째 층은 2홉 간선으로, 두 번째 층은 1홉 간선으로 계산한다. 시드 노드의 출력만 손실에 쓴다.
4. 배치의 양성 쌍은 뽑힌 간선에서 제외한다 (5.6절 3단계의 규칙과 같다).

- 이웃 추출은 GPU 에서 수행한다. 관계마다 유입 간선을 도착 노드별로 묶어 두고, 에폭마다 순서를 섞은 뒤 노드별로 연속 구간을 잘라 쓴다. 같은 간선을 중복해서 뽑지 않는다.
- 모든 간선이 과제–기업 간선이므로 표본 그래프도 이분 그래프다.
- 전체 노드 임베딩(평가와 저장용)은 표본 없이 계산한다. 층마다 도착 노드를 5만 개씩 나누어 그 노드의 모든 유입 간선으로 계산하므로, 결과는 전체 그래프 계산과 같고 메모리에는 한 묶음의 간선만 올라간다.
- 모든 유입 간선을 남기면 표본 그래프의 출력이 전체 그래프 계산과 일치함을 단위 테스트로 확인했다 (`tests/test_neighbor_sampler.py`).

미니배치 학습의 설정과 실측 규모는 다음과 같다.

| 항목 | 값 |
|---|---|
| 배치 크기 (양성 쌍) | 1,024 (에폭당 130 스텝) |
| 이웃 수 (1홉 / 2홉, 노드·관계당) | 10 / 5 |
| 스텝당 시드 노드 | 약 36,000 개 (양성 + 음성 20개 × 양방향) |
| 스텝당 표본 그래프 | 노드 약 57만 개, 간선 약 469만 개(첫 층) + 약 85만 개(둘째 층) |
| 에폭당 시간 | 약 3.7분 |
| 메모리 | 약 70GB (GPU 메모리 상한 60% 적용, `gnn.gpu_memory_fraction`) |

음성 표본이 양성당 20개씩 양방향으로 들어가므로 시드 노드가 많고, 2홉까지 가면 표본 그래프가 전체 노드의 약 70% 를 포함한다. 간선은 전체(약 2,800만 개)의 약 5분의 1 이다.

**관계별 변환의 계산 방식 수정** (`FastHGTConv`). 미니배치로 바꾼 직후에는 스텝당 역전파에 5 ~ 10초가 걸렸다. 원인은 PyG `HGTConv` 가 간선 타입 · 헤드별 Key / Value 변환 결과를 미리 잡아 둔 텐서에 구간별로 써넣는 방식에 있었다. 이 쓰기 연산의 역전파는 구간마다 전체 텐서를 복사하므로, 비용이 간선 타입 수의 제곱과 노드 수에 비례한다. 확장 그래프는 간선 타입이 14개(역방향 포함)라 이 비용이 지배적이었다. 간선 타입마다 헤드 묶음 행렬곱 한 번으로 계산하도록 바꿔, 같은 크기의 그래프에서 역전파가 9.6초에서 0.8초로 줄었다. 파라미터와 출력은 `HGTConv` 와 같고, 단위 테스트로 일치를 확인했다.

**LightGCN 과의 차이.** LightGCN 은 간선 타입을 구분하지 않고 차수로만 정규화해 더한다. HGT 는 간선 타입별 변환과 어텐션을 학습하며, 층마다 비선형 변환이 있다. `HGTConv` 는 간선 가중치 인자를 받지 않으므로, 간선 타입 가중치는 손실에만 반영된다.

### 5.4 LightFM 구현 (`src/baselines/lightfm_baseline.py`, `scripts/baseline_lightfm.py`)

PyPI 배포본이 현재 환경에서 빌드되지 않아 GitHub 소스(LightFM 1.17)를 직접 빌드해 사용했다.


- **상호작용 행렬**: 세 관계의 학습 간선을 합친 (과제 × 기업) 이진 희소 행렬. 같은 쌍이 여러 관계에 있으면 가장 큰 관계 가중치를 표본 가중치로 쓴다.
- **피처**: 과제·기업 모두 bge-m3 임베딩 1024차원만 쓴다 (`identity_mode: none`). 노드별 ID 피처가 없으므로 모델은 피처 차원마다 64차원 잠재 벡터를 하나씩 학습한다.
- **잠재 벡터**: 노드의 잠재 벡터는 피처 값으로 가중한 피처 임베딩의 합이다. 즉 bge-m3 벡터에 학습된 (1024 × 64) 행렬을 곱한 것과 같다.

```
q_p = x_p · E_과제 ,   q_c = x_c · E_기업 ,   점수(p, c) = q_p · q_c + b_p + b_c
```

- **손실**: WARP. 양성 기업보다 점수가 높은 음성 기업이 나올 때까지 무작위로 뽑고, 몇 번 만에 찾았는지로 순위를 추정해 갱신 크기를 정한다.
- **설정**: 잠재 차원 64, 에폭 10, 학습률 0.05.
- **추론**: 쿼리 과제와 전체 기업의 점수를 계산해 상위 100개를 반환한다. `--save-candidates` 옵션으로 표본 쿼리의 상위 100개를 LLM 매칭 비교용 파일로 저장한다.
- **GNN 과의 차이**: 그래프 전파가 없다. 관계 정보는 손실을 통해 피처 변환 행렬을 학습하는 데만 쓰인다.

### 5.5 bge-m3 + LLM 매칭 구현

`~/work/apollo` 의 매칭 방식을 held-out 평가에 맞게 옮겼다.

1. **후보 검색**: 쿼리 과제의 bge-m3 벡터와 전체 기업 벡터의 코사인 유사도 상위 100개를 후보로 뽑는다.
2. **LLM 채점**: 쿼리 과제 문서와 후보 기업 문서 20개를 한 프롬프트에 넣고, LLM 이 후보마다 0~100 적합도 점수와 근거를 JSON 으로 낸다. 프롬프트는 apollo 의 과제→기업 채점 프롬프트와 같다. 응답에서 빠진 후보는 10개씩 묶어 한 번 재시도한다.
3. **재랭킹**: 후보 100개를 LLM 점수 내림차순으로 정렬하고, 동점은 임베딩 유사도로 가른다.

| 항목 | 값 |
|---|---|
| LLM | `Qwen/Qwen3.6-35B-A3B-FP8` (vLLM 오프라인 엔진, docker `vllm-apollo:latest`) |
| 컨텍스트 / 최대 출력 | 24,576 토큰 / 3,500 토큰 |
| 온도 | 0.0 |
| GPU 메모리 사용률 | 0.70 (운영 규칙 상한 0.85) |
| 문서 구성 | 과제: 과제명·연도·키워드·과제설명문 / 기업: 업체명·산업분류·키워드·기업설명문 |

**재랭킹 깊이 확장.** 후보를 상위 100개에서 200, 300, 500개로 넓힌 실험도 수행했다 (`config/llm_match.yaml` 의 `candidates.llm_depths`).

- 깊이별로 새로 들어온 후보만 추가로 채점한다. 상위 100개의 채점 결과는 그대로 재사용한다.
- 채점 순서는 깊이 우선이다. 모든 쿼리를 깊이 200 까지 채점한 뒤 300, 500 으로 내려가므로, 중간에 멈춰도 얕은 깊이의 결과는 전체 쿼리에 대해 얻는다.
- 더 깊은 후보 목록을 만들 때 이미 채점한 목록은 앞부분에 그대로 둔다. 유사도가 같은 후보의 순서가 바뀌어 채점한 쌍이 어긋나는 것을 막기 위해서다.
- 평가는 깊이를 지정해 실행한다 (`scripts/llm_match_eval.py --topn 200`). 깊이 N 의 재랭킹은 상위 N 개 후보를 LLM 점수로 다시 정렬한 것이다.

**기업명 가리기**: 과제설명문에는 수행기관명이 적혀 있는 경우가 많다("(주)A 에서 수행하는 이 과제는 …"). 그대로 두면 LLM 이 업체명 일치만으로 정답을 맞히게 된다. 그래서 쿼리 과제와 간선으로 연결된 기업의 이름은 과제 문서에서 `○○○` 로 가린다.

### 5.6 GNN 학습에서 확인된 문제와 수정 경과

GNN 학습은 네 차례 설정을 바꿨다. 각 단계의 설정, 결과, 원인을 기록한다. 수치는 모두 실측이다.

| 단계 | 음성 샘플 (양성당) | 메시지 전파 간선 | 손실 방향 | 결과 |
|---|---|---|---|---|
| 1. 기본 설정 | 전체 기업에서 무작위 5개 | 실제 관계 3종 | 과제 → 기업 | HGT 붕괴 (Hits@10 0.001). LightGCN 도 과제 벡터가 거의 동일 |
| 2. 하드 네거티브 방식 | 20개 = 하드 16 + 무작위 4 | 실제 관계 + 유사도 상위 10 | 양방향 | LightGCN 은 붕괴 해소. HGT 는 다시 실패 (에폭 10 에서 Hits@10 0.003 이하) |
| 3. 수정 방식 | 20개 = 하드 8 + 간선 있는 노드 8 + 무작위 4 | 2단계와 같되, 배치의 양성 쌍은 제외 | 양방향 | LightGCN Hits@100 약 2배로 상승. HGT 는 느리게 학습 |
| 4. 확장 그래프 | 3단계와 같음 | 3단계 + 특허 · 키워드 · 상속 간선, held-out 쌍 제외, 간선 가중치 반영 | 양방향 | LightGCN 은 3단계와 거의 같음. HGT 는 전체 그래프 학습이 메모리에 들어가지 않아 미니배치 학습으로 전환했으나 검색 성능이 낮음 (7.7절) |

**1단계의 문제.** 기업의 94.9% 는 학습 간선이 없다 (간선 있는 기업 19,971 곳 / 392,032 곳). 양성 기업은 항상 간선이 있고, 무작위 음성은 거의 항상 간선이 없다. 모델이 "간선 있는 기업인가"만 구분해도 손실이 충분히 내려가므로, 과제별 차이를 학습하지 않았다. 30 에폭 학습 후 무작위 과제 쌍의 코사인 평균이 HGT 1.000, LightGCN 0.999 였다.

**2단계: 하드 네거티브와 유사도 간선.** 저장소의 이전 실험 방식(`scripts/run_sweep.py`)을 따랐다 (`scripts/run_gnn_recipe.sh`).

- 유사도 간선: 각 과제의 bge-m3 유사도 상위 10 기업, 각 기업의 상위 10 과제를 메시지 전파 간선으로 추가 (약 786만 개).
- 하드 네거티브: 유사도 상위 100 후보에서 실제 연결 쌍과 상위 10 을 빼고, `1 − 0.5 × 키워드 자카드 − 0.3 × 산업분류 일치 − 0.2 × 이름 자카드` 로 계산한 무관함 점수가 높은 20개를 고른다 (`scripts/build_hard_negatives.py`).
- 음성 20개 중 16개를 하드 네거티브 풀에서, 4개를 전체에서 무작위로 뽑는다. 기업 → 과제 방향 손실을 더한다. 출력 정규화는 하지 않는다.

LightGCN 은 붕괴가 해소되었다 (무작위 과제 쌍의 코사인 평균 0.999 → 0.001). 100 에폭까지의 곡선은 다음과 같다 (전체 held-out 쿼리, 과제 → 기업).

| 에폭 | 학습 손실 | 기술이전 Hits@10 / @100 | 사업화 Hits@10 / @100 | 과제수행 Hits@10 / @100 |
|---|---|---|---|---|
| 10 | 0.239 | 0.046 / 0.185 | 0.037 / 0.145 | 0.058 / 0.193 |
| 20 | 0.152 | 0.064 / 0.210 | 0.054 / 0.184 | 0.074 / 0.233 |
| 30 | 0.110 | 0.066 / 0.203 | 0.062 / 0.186 | 0.079 / 0.242 |
| 40 | 0.086 | 0.065 / 0.213 | 0.065 / 0.192 | 0.086 / 0.247 |
| 60 | 0.059 | 0.072 / 0.206 | 0.063 / 0.188 | 0.092 / 0.242 |
| 80 | 0.045 | 0.063 / 0.207 | 0.065 / 0.192 | 0.094 / 0.237 |
| 100 | 0.038 | 0.056 / 0.198 | 0.066 / 0.190 | 0.094 / 0.235 |

학습 손실은 계속 내려가지만 held-out 지표는 40~60 에폭에서 멈췄다. 기술이전은 60 에폭 이후 조금 내려가 과적합 조짐을 보인다. 에폭을 더 늘려도 개선될 가능성이 낮아 100 에폭에서 멈췄다. 지표가 가장 좋은 에폭을 고르면 테스트 데이터로 모델을 선택하는 셈이므로, 미리 정한 100 에폭 모델을 쓴다.

HGT 는 같은 방식에서 다시 실패했다 (에폭 10 시점).

| 항목 | 값 |
|---|---|
| 학습 손실 | 0.0245 |
| held-out Hits@10 (기술이전 / 사업화 / 과제수행) | 0.003 / 0.001 / 0.001 |
| 학습 간선 자체의 Hits@10 (기술이전 / 과제수행) | 0.025 / 0.043 |
| held-out 정답의 순위 중앙값 | 약 11,400 위 |
| 기업 벡터 크기 평균 (간선 있는 기업 / 없는 기업) | 6.2 / 20.8 |

held-out 정답의 순위 중앙값은 간선 있는 기업 약 2만 곳 안에서 무작위로 놓았을 때의 값(약 1만 위)과 같다. 즉 HGT 는 여전히 "간선 있는 기업인가"만 구분했다. 하드 네거티브가 이를 막지 못한 이유는 하드 네거티브 풀의 85.8% 가 간선 없는 기업이기 때문이다. 양성은 항상 간선 있는 기업이므로, 음성 대부분이 간선 유무만으로 구분된다. LightGCN 은 층별 변환이 없어 이 지름길을 잘 이용하지 못했고, HGT 는 간선 타입별 어텐션으로 쉽게 잡아냈다.

**3단계: 수정.** 두 가지 옵션을 추가했다. 기본값은 기존 동작과 같다 (`config/train.yaml` 의 `gnn.warm_neg_ratio`, `gnn.mask_batch_edges`).

1. **간선 있는 노드에서 음성 추출** (`warm_neg_ratio`, `src/training/sampler.py`). 무작위 음성 중 지정한 비율을 학습 간선이 있는 노드에서 뽑는다. 양성과 같은 종류의 기업이 음성으로 들어오므로, 간선 유무만으로는 손실을 낮출 수 없다.
2. **배치의 양성 쌍을 메시지 전파에서 제외** (`mask_batch_edges`, `src/training/trainer.py`). 스텝마다 그 배치에서 점수를 매기는 (과제, 기업) 쌍을 모든 실제 관계와 역방향의 전파 간선에서 뺀다. held-out 쌍은 추론 때 직접 이웃이 아니므로, 학습 때도 같은 조건을 만든다.

**이전 실험 수치와의 관계.** 저장소에 기록된 이전 GNN 실험 수치(예: HGT Hits@10 0.38 ~ 0.41)는 3.3절의 held-out 누설이 있던 그래프에서 측정한 것이다. 그 그래프에서는 held-out 쌍의 38 ~ 49% 가 다른 관계의 학습 간선으로 남아 있었으므로, 이번 결과와 직접 비교할 수 없다.

## 6. 실험 방법

### 6.1 평가 과제

쿼리는 held-out 간선을 가진 과제이고, 정답은 그 과제의 held-out 상대 기업이다. 각 방법은 쿼리마다 반대편 타입 전체 노드 중 상위 100개를 순위대로 낸다. 두 방향을 평가한다.

| 방향 | 쿼리 | 후보 | 쿼리당 정답 수 (held-out) | 정답에 학습 간선이 있는 비율 |
|---|---|---|---|---|
| 과제 → 기업 (p2c) | held-out 과제 8,553 개 | 기업 392,032 곳 | 평균 1.04, 1개인 쿼리 98.2% | 85.3% |
| 기업 → 과제 (c2p) | held-out 기업 6,363 곳 | 과제 430,374 개 | 평균 1.39, 1개인 쿼리 74.7% | 14.1% |

처음에는 과제 → 기업만 평가했고, 이후 기본 평가 방향을 기업 → 과제로 바꿨다 (`config/llm_match.yaml` 의 `queries.directions`). 기업 → 과제는 정답이 여러 개인 쿼리가 많지만, 찾아야 할 정답 과제의 85.9% 가 학습 간선이 없는 과제라 연결 이력에 의존하는 모델에게는 더 어려운 조건이다. 간선 종류를 합쳐도 과제 → 기업의 정답 수는 늘지 않는다(과제의 94% 가 기업 한 곳과만 연결).

### 6.2 쿼리 표본

LLM 채점 비용 때문에 관계별로 쿼리 200개를 시드 42 로 무작위 추출한다 (`config/llm_match.yaml` 의 `queries.max_per_relation: 200`). 두 관계에서 동시에 뽑힌 쿼리는 한 번만 센다. 과제 → 기업은 **과제 599개**, 기업 → 과제는 **기업 591곳**이 쿼리다. 모든 방법을 같은 쿼리에서 평가한다.

LightGCN, LightFM, HGT 는 학습 직후 전체 held-out 쿼리(8,553개)에 대한 지표도 따로 보고한다.

### 6.3 평가 지표

K 는 10 과 100 이다 (`src/eval/ranking.py`).

| 지표 | 정의 |
|---|---|
| Hits@K | 상위 K 안에 정답이 하나라도 있는 쿼리의 비율 |
| Recall@K | 쿼리별로 정답 중 상위 K 안에 들어온 비율의 평균 |
| NDCG@K | 정답의 순위를 반영한 지표. 정답이 위에 있을수록 크다 (정답 여부는 이진) |

지표는 관계별(기술이전, 사업화, 과제수행)과 전체, 그리고 과제 문서에 연결 기업명이 있는 쿼리와 없는 쿼리(3.5절)로 나누어 보고한다. 과제 → 기업 방향에서는 쿼리당 정답이 대부분 1개라 Hits 와 Recall 이 거의 같다.

bge-m3 + LLM 은 bge-m3 상위 100개의 순서만 바꾸므로, Hits@100 과 Recall@100 은 bge-m3 단독과 같다. LLM 의 효과는 @10 지표와 NDCG 에 나타난다. 재랭킹 깊이를 200 이상으로 넓히면(5.5절) 100위 밖의 후보가 100위 안으로 올라올 수 있어 Hits@100 도 달라진다.

### 6.4 지표 수준의 해석

지표의 절대값은 낮아 보이지만 조건을 함께 봐야 한다.

- 후보가 약 39만 개이고 정답은 대부분 1개다. 무작위 추천의 Hits@100 은 0.0255% 다.
- 과제 → 기업에서 쿼리 과제의 85.9% 는 학습 그래프에 간선이 없다. 사실상 신규 과제에 대한 추천이다.
- 정답이 1개면 NDCG 는 정답이 10위일 때 0.29, 50위일 때 0.18 이고 못 찾으면 0 이다.
- 기록된 그 기업만 정답으로 치므로, 기술적으로 적합한 다른 기업을 추천해도 오답이다. 지표는 실제 매칭 품질의 하한에 가깝다.

후보 수와 모델 결합에 따른 정답 포함률은 다음과 같다 (held-out 쌍 3,000 개 표본, 과제 → 기업, 5.6절 3단계 LightGCN).

| 방법 | @10 | @100 | @500 | @1000 | @5000 | 정답 순위 중앙값 |
|---|---|---|---|---|---|---|
| LightGCN | 0.147 | 0.367 | 0.559 | 0.644 | 0.802 | 305 |
| bge-m3 | 0.138 | 0.297 | 0.429 | 0.502 | 0.671 | 974 |
| 둘 중 더 좋은 순위 | 0.237 | 0.491 | 0.675 | 0.749 | 0.883 | 107 |

정답 기업의 상태별 Hits@100:

| 정답 기업 | 비중 | LightGCN | bge-m3 |
|---|---|---|---|
| 학습 간선이 있는 기업 | 85% | 0.36 ~ 0.44 | 0.17 ~ 0.32 |
| 학습 간선이 없는 기업 | 15% | 0.00 ~ 0.01 | 0.10 ~ 0.30 |

LightGCN 은 학습 간선이 없는 상대를 거의 찾지 못하고, bge-m3 는 연결 이력과 무관하게 찾는다. 두 모델이 서로 다른 정답을 찾으므로 후보를 합치면 포함률이 오른다. 3.8절의 간선 확장은 간선 없는 노드에 대한 이 약점을 줄이려는 것이다.

## 7. 수행 과정

아래 명령은 저장소 루트에서 실행한다.

| 단계 | 명령 | 내용 | 소요 시간(실측 또는 추정) |
|---|---|---|---|
| 1 | `make setup` | 가상환경 생성, 데이터 디렉터리 연결 | 수 분 |
| 2 | `make merge-projects` | bge-m3 과제 테이블의 다년도 과제 병합 → `data/raw_merged/` | 약 2분 |
| 3 | `make data` | 그래프 생성, held-out 분리, 누설 쌍 제거 | 약 1분 |
| 4 | `make sync-code`, `make sync-data` | 원격 장비로 코드와 그래프 전송 | 1분 미만 |
| 5 | `python scripts/train_gnn.py --layer-type lightgcn --device cuda` | LightGCN 학습과 z 저장 | 약 3분 (에폭당 약 4초) |
| 6 | `python scripts/baseline_lightfm.py --save-candidates` | LightFM 학습, 표본 쿼리 후보 저장 | 약 2분 |
| 7 | `python scripts/train_gnn.py --layer-type hgt --device cuda` (원격) | HGT 학습과 z 저장 | 약 45분 (에폭당 약 90초) |
| 8 | `make llm-prepare` | 표본 쿼리의 모델별 상위 100 후보와 LLM 채점 작업 생성 | 약 3분 |
| 9 | `make llm-score SHARD=0 NUM_SHARDS=2` (로컬), `SHARD=1` (원격) | LLM 적합도 채점 (599 쿼리 × 100 후보 = 약 3,000 프롬프트) | 장비 2대로 약 2~3시간 (추정) |
| 10 | `make sync-results` | 원격 채점 결과 회수 | 1분 미만 |
| 11 | `make llm-eval` | 같은 쿼리에서 네 방법의 6개 지표 산출 → `metrics_p2c.json` | 1분 미만 |

진행 중 처리한 사항은 다음과 같다.

- **임베딩 교체**: pro-sroberta(768차원)에서 bge-m3(1024차원)로 바꾸고, 벡터 없는 기업 425,085 곳을 제외했다. 이전 pro-sroberta 그래프는 `~/data/apollo.data/processed/pro_sroberta/` 에 보관했다.
- **held-out 누설 수정**: 3.3절의 문제를 발견해 그래프를 다시 만들고 세 모델을 모두 다시 학습했다. 수정 전 그래프로 얻은 수치는 쓰지 않는다.
- **GNN 학습 방식 변경**: 기본 설정에서 HGT 가 붕괴해 학습 방식을 두 차례 바꿨다. 경과와 원인, 수정 내용은 5.6절에 정리했다. 에폭 수는 10 에폭마다 held-out 지표를 측정해 수렴 여부를 보고 정한다 (기본 100 에폭, 필요하면 저장된 모델에서 이어서 연장).
- **기업명 제거 재임베딩**: 3.5절의 문제 때문에 3.6절의 재임베딩을 수행했고, 이후의 실험은 모두 재임베딩한 벡터로 다시 수행했다.
- **그래프 확장**: 실제 관계 간선이 있는 노드가 적어, 특허 간선(학습 양성)과 키워드·상속 간선(메시지 전파 전용)을 추가했다 (3.8절). 이 과정에서 특허 데이터와 기존 유사도 간선에 held-out 정답 쌍이 들어 있음을 확인하고 모두 제거했다.
- **평가 방향 추가**: 기본 평가 방향을 기업 → 과제로 바꾸고, 과제 → 기업 결과도 함께 보고한다 (6.1절).
- **재랭킹 깊이 확장**: bge-m3 후보를 상위 200, 300, 500개까지 넓혀 추가 채점했다 (5.5절, 7.6절). 과제 → 기업 11,980 프롬프트에 18.1시간, 기업 → 과제 11,820 프롬프트에 16.1시간이 걸렸다. 채점 감시·재시작·평가는 `scripts/llm_depths_followup.sh` 로 자동화했다.
- **HGT 미니배치 전환**: 확장 그래프에서 HGT 전체 그래프 학습이 메모리 부족으로 중단되어 미니배치 이웃 샘플링으로 바꿨다 (5.3절, 5.6절).
- **채점 재개**: LLM 채점은 프롬프트 64개마다 결과를 저장하며, 같은 명령을 다시 실행하면 이어서 진행한다. 쿼리 순서가 무작위라 중간까지 끝난 쿼리만으로도 평가할 수 있다.

### 7.1 참고: 기업명이 들어간 벡터 기준의 중간 결과 (실측)

재임베딩 전에 진행하던 실험의 결과다. LLM 채점이 표본의 절반(300쿼리)까지 끝난 시점에 평가했다. 기업명 누설(3.5절)이 있는 벡터 기준이며, LightGCN 은 학습이 붕괴한 모델이므로 **최종 결과로 쓰지 않고 참고용으로만 둔다.** HGT 는 학습 실패로 제외했다.

전체 관계 합산 (300쿼리):

| bge-m3 | 0.573 | 0.650 | 0.469 | 0.485 | 0.567 | 0.643 |
| bge-m3 + LLM | 0.413 | 0.650 | 0.313 | 0.361 | 0.408 | 0.643 |
| LightFM | 0.197 | 0.383 | 0.117 | 0.153 | 0.195 | 0.380 |
| LightGCN (붕괴) | 0.303 | 0.380 | 0.245 | 0.260 | 0.303 | 0.377 |

쿼리 집단별 Hits@10:

| 방법 | 연결 기업명 있는 쿼리 (176개) | 연결 기업명 없는 쿼리 (124개) |
|---|---|---|

- LLM 재랭킹은 Hits@10 을 0.573 에서 0.413 으로 낮췄다. 임베딩이 기업명으로 상위에 올린 정답을, 기업명이 가려진 문서를 본 LLM 이 기술 내용만으로 다시 판단하면서 순위가 내려간 것이다.
- 연결 기업명이 없는 쿼리에서는 LLM 재랭킹 전후가 비슷하다 (Hits@10 0.194 → 0.177, NDCG@10 0.121 → 0.140). 쿼리가 124개라 이 차이는 오차 범위 안이다.
- LLM 응답 누락은 1,500 프롬프트에서 0건이었고, 프롬프트당 평균 5.4초가 걸렸다.

### 7.7 결과: 확장 그래프의 HGT 미니배치 학습 (실측)

5.3절의 미니배치 설정(배치 1,024, 이웃 수 10 / 5)으로 확장 그래프에서 HGT 를 100 에폭 학습했다 (에폭당 222초, 총 약 6.5시간). 전체 held-out 쌍(세 관계 합산, 중복 제거 8,870쌍)으로 평가했다.

| 모델 | 과제 → 기업 Hits@10 | 과제 → 기업 Hits@100 | 기업 → 과제 Hits@10 | 기업 → 과제 Hits@100 |
|---|---|---|---|---|
| LightGCN, 확장 그래프 | 0.151 | 0.375 | 0.009 | 0.033 |
| HGT, 확장 그래프, 미니배치 | 0.008 | 0.056 | 0.001 | 0.008 |

- 학습 손실은 0.420 에서 0.034 까지 계속 내려갔지만 검색 성능은 오르지 않았다. 과제 → 기업 Hits@100 은 10 에폭 0.03 ~ 0.05 에서 100 에폭 0.04 ~ 0.07 로 거의 그대로이고, 기업 → 과제는 20 에폭 이후 오히려 내려갔다.
- **원인: 학습과 추론의 이웃 구성 차이.** 저장된 임베딩은 held-out 쌍뿐 아니라 학습 간선도 찾지 못했다 (학습 간선 과제 → 기업 Hits@100 0.053). 과적합이 아니라는 뜻이다. 같은 모델을 학습 때와 같은 이웃 수(10 / 5)로 표본 추론하면 아래 표처럼 성능이 크게 오른다.
- HGT 는 한 노드로 들어오는 모든 관계의 간선에 어텐션을 함께 정규화한다. 학습 때는 관계별 이웃을 층에 따라 최대 5 ~ 10개만 보지만 전체 이웃 추론에서는 유사도 · 키워드 · 상속 간선이 모두 들어와(유사도 간선의 절반이 10개 한도 밖) 실제 관계 간선의 비중이 달라진다. 이 차이는 이웃이 많은 일부 노드가 아니라 전 노드에서 나타났다 (표본 추론과 전체 추론 임베딩의 코사인 평균: 과제 0.60, 기업 0.83).
- 이웃 수를 학습 때와 다르게 주면 어느 쪽으로든 성능이 떨어진다 (3 / 2: 과제 → 기업 Hits@100 0.033, 30 / 15: 0.144). 표본 추론을 8회 평균해도 1회와 같다.

| HGT 추론 방식 (100 에폭 모델) | 과제 → 기업 Hits@10 | 과제 → 기업 Hits@100 | 기업 → 과제 Hits@10 | 기업 → 과제 Hits@100 |
|---|---|---|---|---|
| 전체 이웃 (위 표의 값) | 0.008 | 0.056 | 0.001 | 0.008 |
| 이웃 표본 10 / 5 (학습과 동일) | 0.053 | 0.206 | 0.045 | 0.128 |
| 점수 상위 이웃 고정 10 / 5 로 재학습 (학습 · 추론 동일) | 0.050 | 0.193 | 0.042 | 0.113 |
| 점수 상위 이웃 고정 20 / 10, 배치 512 로 재학습 | 0.058 | 0.201 | 0.044 | 0.117 |

- **점수 상위 이웃 고정 재학습** (`gnn.minibatch.neighbor_selection: top_score`). 노드 · 관계마다 점수가 높은 간선부터 고정해 학습과 추론에 같은 이웃을 쓰도록 하고 100 에폭을 다시 학습했다 (에폭당 166초). 점수는 키워드 · 상속 간선은 캐시의 점수, 그 밖의 관계는 양 끝 노드 bge-m3 벡터의 코사인 유사도다. 학습 · 추론 불일치는 없어졌지만 성능은 무작위 표본으로 학습한 모델의 표본 추론과 같은 수준이고 조금 낮다. 20 에폭 이후로는 지표가 거의 오르지 않았다. 즉 이웃을 고르는 방식은 성능을 좌우하지 않으며, 남은 차이는 모델 · 학습 설정 쪽에 있다.
- **이웃 수를 20 / 10 으로 늘린 재학습** (배치 512, 에폭당 421초, 100 에폭 약 11.7시간). 10 / 5 보다 조금 높지만 차이가 0.01 이내다 (NDCG@10: 과제 → 기업 0.026 → 0.031, 기업 → 과제 0.023 → 0.023). 이웃 수를 두 배로 늘려도 성능은 사실상 그대로다.
- 표본 추론 기준으로 HGT 는 과제 → 기업에서 LightGCN(0.151 / 0.375)보다 낮고, 기업 → 과제에서는 LightGCN(0.009 / 0.033)의 약 4배다. 표본 추론은 진단용으로 측정한 값이며 학습 스크립트의 평가 경로에는 아직 반영하지 않았다.
- HGT 후보는 LLM 재랭킹 비교에 넣지 않았다.

### 7.8 결과: LightGCN 요인 분리 실험 (실측)

7.4절에서 확장 그래프가 기업 → 과제만 개선한 이유를 가르기 위해, 확장 전후의 차이를 하나씩 더해 가며 LightGCN 을 각각 100 에폭 학습했다. 전체 held-out 쌍 합산(과제 쿼리 8,553개, 기업 쿼리 6,363개) 결과다.

| 조건 | 과제 → 기업 Hits@10 | 과제 → 기업 Hits@100 | 기업 → 과제 Hits@10 | 기업 → 과제 Hits@100 |
|---|---|---|---|---|
| 확장 전 그래프 | 0.150 | 0.376 | 0.002 | 0.018 |
| A0: 유사도 간선에서 held-out 쌍 제거 | 0.142 | 0.370 | 0.002 | 0.018 |
| A1: A0 + 간선 가중치를 메시지에 반영 | 0.117 | 0.333 | 0.004 | 0.022 |
| B: A1 + 특허 간선 | 0.143 | 0.356 | 0.005 | 0.026 |
| C: B + 키워드 · 상속 간선 (7.4절의 확장 그래프) | 0.151 | 0.375 | 0.009 | 0.033 |

- **held-out 쌍 제거**: 과제 → 기업 Hits@10 을 0.008 낮춘다. 확장 전 결과에는 정답 쌍 일부(1,392쌍)가 유사도 간선으로 남아 있었다.
- **간선 가중치 반영**: 과제 → 기업을 가장 크게 낮추고(0.142 → 0.117), 기업 → 과제는 조금 올린다.
- **특허 · 키워드 · 상속 간선**: 두 방향 모두 올린다. 과제 → 기업은 가중치 반영으로 잃은 만큼을 회복해 확장 전 수준으로 돌아온다.
- 따라서 추가한 간선은 과제 → 기업에도 도움이 되며, 7.4절에서 차이가 없어 보인 것은 가중치 반영의 손실과 상쇄됐기 때문이다. "확장 그래프 + 가중치 반영 끔" 조건은 측정하지 않았다.
- 조건마다 시드 하나로 한 번씩 학습했으므로 0.005 안팎의 차이는 잡음일 수 있다. 하드 네거티브 풀은 모든 조건에 같은 파일(특허 쌍 제외)을 썼다.

### 7.9 결과: 유사도 간선 제거 실험 (실측)

유사도 간선은 양 끝 노드의 bge-m3 벡터가 이미 가까운 쌍이므로 학습에 새 정보를 주지 않을 수 있다. 이를 확인하기 위해 확장 그래프(7.8절의 C)에서 유사도 간선을 빼고 LightGCN 을 각각 100 에폭 학습했다. 나머지 설정과 하드 네거티브 풀은 C 와 같다. 전체 held-out 쌍 합산 결과다.

| 조건 | 유사도 간선 | 키워드 · 상속 간선 | 과제 → 기업 Hits@10 | 과제 → 기업 Hits@100 | 기업 → 과제 Hits@10 | 기업 → 과제 Hits@100 |
|---|---|---|---|---|---|---|
| C: 확장 그래프 | 있음 | 있음 | 0.151 | 0.375 | 0.009 | 0.033 |
| B: 유사도만 | 있음 | 없음 | 0.143 | 0.356 | 0.005 | 0.026 |
| S1: 유사도만 제거 | 없음 | 있음 | 0.131 | 0.346 | 0.005 | 0.028 |
| S2: 계산 간선 전부 제거 | 없음 | 없음 | 0.117 | 0.323 | 0.005 | 0.026 |

- **유사도 간선은 도움이 된다.** 빼면 과제 → 기업 Hits@10 이 0.151 → 0.131 로 떨어진다. 키워드 · 상속 간선이 없는 상태에서도 같은 방향이다 (B 0.143, S2 0.117).
- **키워드 · 상속 간선의 기여는 유사도보다 작다.** S2 에 키워드 · 상속을 더하면 Hits@10 이 0.014 오르고, 유사도를 더하면 0.026 오른다.
- **기업 → 과제**는 세 종류가 모두 있을 때만 0.009 / 0.033 으로 조금 오르고, 나머지 조건은 0.005 수준으로 차이가 없다.
- NDCG 도 같은 순서다 (과제 → 기업 NDCG@10: C 0.086, B 0.082, S1 0.074, S2 0.066).
- 원인은 확인하지 않았다. S1 에서도 상속 간선이 거의 모든 노드에 있으므로(과제 99.9%, 기업 100%) "간선이 없는 노드를 채워 준다"는 설명은 맞지 않는다. 조건마다 시드 하나로 한 번씩 학습한 결과다.

### 7.10 결과: 후보를 실제 관계 노드로 제한한 평가 (실측)

전체 후보(과제 430,374, 기업 392,032)가 많아 Hits 가 낮게 나오는지 확인하기 위해, 재학습 없이 후보만 줄여 평가했다. 후보는 기술이전 · 사업화 · 수행 간선(학습 + held-out)이 하나라도 있는 노드로, 기업 21,204개와 과제 61,260개다. 전체 held-out 쌍 합산이며 각 칸은 Hits@10 / Hits@100 이다.

| 모델 | 방향 | 전체 후보 | 제한 후보 |
|---|---|---|---|
| bge-m3 | 과제 → 기업 | 0.137 / 0.297 | 0.230 / 0.467 |
| LightGCN, 확장 그래프 | 과제 → 기업 | 0.151 / 0.375 | 0.151 / 0.377 |
| HGT, 점수 상위 이웃 고정 10 / 5 | 과제 → 기업 | 0.049 / 0.193 | 0.050 / 0.194 |
| bge-m3 | 기업 → 과제 | 0.120 / 0.278 | 0.174 / 0.378 |
| LightGCN, 확장 그래프 | 기업 → 과제 | 0.008 / 0.033 | 0.008 / 0.034 |
| HGT, 점수 상위 이웃 고정 10 / 5 | 기업 → 과제 | 0.042 / 0.113 | 0.051 / 0.159 |
| HGT, 점수 상위 이웃 고정 20 / 10 | 과제 → 기업 | 0.058 / 0.201 | 0.058 / 0.203 |
| HGT, 점수 상위 이웃 고정 20 / 10 | 기업 → 과제 | 0.044 / 0.117 | 0.054 / 0.171 |

- **후보 수는 GNN 의 한계가 아니다.** 후보를 약 18분의 1로 줄여도 LightGCN 과 HGT 의 과제 → 기업 수치는 그대로다. 두 모델의 상위 100 은 이미 실제 관계가 있는 기업으로만 채워져 있다.
- **제한 후보 안에서는 bge-m3 가 가장 높다.** 전체 후보에서 LightGCN 이 bge-m3 보다 높았던 것은 실제 관계가 있는 노드를 가려낸 효과이고, 그 안에서 정답을 고르는 능력은 bge-m3 보다 낮다.
- HGT 는 기업 → 과제에서만 조금 오른다 (Hits@100 0.113 → 0.159).
- 제한 후보에는 held-out 정답 노드가 항상 들어 있다. 실제 서비스에서는 어떤 노드가 정답 후보인지 미리 알 수 없으므로 이 수치는 실제보다 유리한 조건의 값이다.

|---|---|---|---|---|

- HGT 는 100 에폭 시점에도 지표가 조금씩 오르고 있었다 (수행 관계 과제 → 기업 Hits@100: 80 에폭 0.231, 100 에폭 0.242).

- **축소 그래프는 실험용이다.** 서비스에서는 축소 그래프 밖의 과제 369,114개(86%)와 기업 370,828개(95%)가 모두 projection MLP 경로로 추론돼야 하고, 이 경로의 성능은 측정하지 않았다.

## 8. 제한 사항

- 쿼리 표본이 관계별 200개라, Hits@10 이 10% 근처일 때 표준오차가 약 ±2%p 다. 모델 간 차이가 3~4%p 미만이면 우열을 단정하기 어렵다.
- HGT 는 확장 그래프에서 미니배치 학습으로 바꿨으므로, 전체 그래프로 학습한 LightGCN 과 학습 방식이 다르다. 이웃을 표본으로 뽑는 데서 오는 차이가 결과에 섞인다.
- 하이퍼파라미터는 설정 기본값이며 모델별로 따로 튜닝하지 않았다.
- LLM 은 bge-m3 후보만 재랭킹한다. 정답이 bge-m3 후보(깊이 100 ~ 500) 안에 없으면 LLM 이 찾을 수 없다. LightGCN 후보의 LLM 재랭킹은 수행하지 않았다.
- 기업명 가리기는 간선으로 연결된 기업명만 대상으로 한다. 설명문에 다른 형태로 적힌 단서(약칭, 영문명)는 남아 있을 수 있다.
- bge-m3 벡터는 기업명을 제거한 설명문으로 다시 만들었지만(3.6절), 제거 규칙이 잡지 못한 표기가 남아 있을 수 있다. 이 벡터를 초기 피처로 쓰는 LightGCN, LightFM, HGT 도 같은 영향을 받는다.
- 사전 학습된 LLM 이 공개 정보를 통해 특정 과제–기업 관계를 이미 알고 있을 가능성은 통제하지 못한다.
